# Data Dictionary

Generated by `generate_synthetic_company.py` (seed=42). Full tables land in
`data/generated/` (gitignored); small previews are committed in
`data/sample/`. All figures are synthetic — see `docs/case_reference.md`.

## regions.csv (6 rows)

| Column | Type | Description |
|---|---|---|
| `region_id` | string | Primary key, e.g. `R01` |
| `region_name` | string | e.g. "Haryana Belt" |
| `state` | string | Indian state |
| `complexity_index` | int (1–5) | How technically demanding / multi-product-heavy accounts in this region tend to be. Haryana Belt is set to 5 — the region the case names as the site of the 2009 geographic-restructuring coverage failure. |

**Feeds:** Module B (regional cost/complexity input to the structure
simulation), Module C (territory constraints), account/rep generation below.

## accounts.csv (650 rows)

Snapshot of the *current* book of business — used by Modules B and C, which
answer present-day structure and assignment questions, not historical ones.

| Column | Type | Description |
|---|---|---|
| `account_id` | string | Primary key, e.g. `A0001` |
| `account_name` | string | Synthetic company name (Faker) |
| `region_id` | string | FK → regions |
| `product_line` | string | One of: Conveyor Systems, Elevator Systems, Bulk Material Handling, Dumb Waiter (New Product) |
| `annual_revenue_inr` | float | Account's annual revenue contribution. Sum across all accounts ≈ Year-6 company revenue (315M). |
| `complexity_score` | int (1–5) | Derived from region complexity + product line (Dumb Waiter accounts skew higher — untested motion) + noise. |
| `acquisition_year` | int | 2019–2024, recency-weighted (more accounts acquired in later years). |

**Feeds:** Module B (coverage-gap / specialization-depth scoring per
structure), Module C (the optimization's demand side), Module D (account
mix informs the buyer-persona-distance baseline for the new product line).

## reps.csv (119 rows)

Current sales headcount (matches Year-6 `sales_headcount` in
yearly_financials). Represents *today's* actual assignment — mostly a
geography-cum-product combination, echoing the case's own 2013 endpoint.
Module B tests counterfactual structures independently of the
`specialization` field; it isn't a constraint on the simulator, just the
descriptive baseline.

| Column | Type | Description |
|---|---|---|
| `rep_id` | string | Primary key, e.g. `REP001` |
| `rep_name` | string | Synthetic name (Faker, en_IN locale) |
| `region_id` | string | FK → regions (home base) |
| `specialization` | string | Current assignment: one of the 4 product lines, or "Generalist" |
| `annual_cost_inr` | float | Fully-loaded annual cost: base (₹900K) × regional cost-of-living multiplier × tenure premium (+4%/yr) + noise |
| `tenure_years` | int | 0–6 |
| `hire_year` | int | Derived from tenure |

**Feeds:** Module B (cost per structure), Module C (the optimization's
supply side / decision variables), Module A (reconciles with
`sales_headcount` in yearly_financials).

## yearly_financials.csv (6 rows, 2019–2024)

The historical trajectory Module A's diagnostic ratio runs against.
Deliberately engineered (not fitted) to reproduce the case's core structural
pattern at a sharper scale: **sales headcount grows 5.41x while revenue
grows only 2.10x** over the period — so `sales_opex` outpaces `revenue`
and net income compresses from 55.4M (2019) toward 3.2M (2024), even though
revenue itself never stops growing. That gap, invisible if you only watch
the revenue line, is exactly what Module A exists to catch.

| Column | Type | Description |
|---|---|---|
| `year` | int | 2019–2024 |
| `revenue_inr_m` | float | Net revenue, INR millions. 150.0 → 315.0 (2.10x), smooth convex ramp + mild noise. |
| `cost_of_sales_inr_m` | float | Materials/fabrication cost, ~44%→39% of revenue (mirrors the case's Exhibit 1 drift). |
| `sales_opex_inr_m` | float | `sales_headcount` × per-rep loaded cost (inflating ~6%/yr) — the term that grows fastest. |
| `other_opex_inr_m` | float | After-sales + quality + admin, scales with (total − sales) headcount. |
| `total_cost_inr_m` | float | Sum of the three cost lines. |
| `net_income_inr_m` | float | `revenue − total_cost`. |
| `sales_headcount` | int | 22 → 119 (5.41x). |
| `total_headcount` | int | Sales + after-sales/quality/support, ~1.55–1.75x sales headcount (per the case's own department split). |

**Feeds:** Module A directly. `sales_headcount` in the final year should
reconcile with `len(reps.csv)` (both are 119).

## Design notes / traceability to the five business questions

- **Q1 (Diagnostic):** `yearly_financials` alone is sufficient — headcount
  vs. revenue ratio, sales-cost-to-total-cost trend.
- **Q2 (Coverage Model):** needs `accounts` (revenue, complexity, product
  line, region) + `reps` (cost, region) to simulate cost/coverage/depth
  per structure.
- **Q3 (Territory Optimizer):** same two tables, reframed as an assignment
  problem — `accounts` = demand nodes, `reps` = capacity/cost.
- **Q4 (GTM Scorer):** `accounts` filtered to `Dumb Waiter (New Product)`
  give the new-product account profile; compared against the other three
  product lines' complexity/region distribution for buyer-persona distance.
- **Q5 (Scenario Dashboard):** re-runs Q1–Q4's computations under perturbed
  growth-rate / specialization-mix / complexity inputs — no new tables
  needed, just parameterized versions of the above.
